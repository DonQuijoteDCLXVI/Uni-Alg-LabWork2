## 2. Приложение 1 — FractalApp (множество Мандельброта)

### 2.1. Математика

Множество Мандельброта — это множество комплексных чисел `c`, для которых последовательность

```
z₀ = 0,   zₙ₊₁ = zₙ² + c
```

остаётся ограниченной. Известно, что если в какой-то момент `|z| > 2`, последовательность гарантированно уходит в бесконечность. Поэтому для каждой точки `c` считают число итераций до «побега» (**escape-time**):

- если побег случился на итерации `i` — точка снаружи множества, цвет зависит от `i`;
- если за `MaxIter` итераций побега нет — точка считается принадлежащей множеству (чёрная).

Пиксель `(px, py)` отображается в `c = (Re, Im)`:

```
Re = CenterX + (px − Width/2)  · Scale
Im = CenterY + (py − Height/2) · Scale
```

Для ускорения перед циклом проверяется принадлежность главной кардиоиде и круглой «луковице» периода 2 — для них ответ известен сразу.

### 2.2. Рекурсивный алгоритм Мариани–Сильвера

**Идея.** Множество Мандельброта **связно и односвязно** (в нём нет «дыр»). Следствие: если вся **граница** прямоугольника имеет одинаковое число итераций, то и вся его **внутренность** такая же. Значит, внутренность можно закрасить, не считая ни одного пикселя внутри.

**Рекурсивная функция** `Process(x0, y0, x1, y1, depth)`:

```
Process(прямоугольник):
    1. Если прямоугольник мал (≤ MinBlock):          ← база рекурсии №2
           посчитать все пиксели напрямую; выйти.
    2. Посчитать ТОЛЬКО пиксели периметра.
    3. Если весь периметр одного цвета:               ← база рекурсии №1
           залить прямоугольник этим цветом; выйти.
    4. Иначе — разделить на 4 квадранта
           и вызвать Process для каждого.             ← рекурсивный шаг
```

Свойства реализации:

- **Две базы рекурсии** (однородная граница и малый размер блока) гарантируют остановку.
- **Кэш итераций** `_iter[]`: общие границы соседних блоков не пересчитываются.
- **Глубина** — около `log₂(800) ≈ 8–10`, так что переполнения стека вызовов нет.
- Блок делится на 4 части (quadtree), поэтому дерево вызовов — это именно **квадродерево** изображения.

**Сложность.** Классический алгоритм всегда считает `W·H` точек — `O(площадь)`. Мариани–Сильвер считает периметры блоков, поэтому для больших однородных областей стоимость близка к `O(периметр)`. Выигрыш тем больше, чем больше на картинке «внутренних» чёрных областей и однородных зон.

### 2.3. Чем алгоритм отличается от других

| Алгоритм | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **Escape-time попиксельный** (в программе — режим «Классический») | Для каждого пикселя считает итерации независимо | Просто, идеально распараллеливается, точный | Всегда `O(W·H)`, чёрные области считаются дольше всего (до `MaxIter`) |
| **Мариани–Сильвер** (рекурсивный, основной) | Квадродерево + заливка по однородной границе | Пропускает большие области, наглядная рекурсия | Возможны единичные неверные пиксели (см. ниже), сложнее распараллелить |
| **Boundary tracing** (трассировка границы) | Обходит границу множества, внутренность заливает | Очень быстр | Сложнее реализация, нужна аккуратная работа с контуром |
| **Perturbation theory / series approximation** | Считает опорную орбиту с высокой точностью, остальные — как малые отклонения | Позволяет зумить на глубины `10⁻¹⁰⁰⁰` и глубже | Очень сложный, нужна арифметика произвольной точности |
| **Buddhabrot** | Рисует не множество, а траектории побегающих точек | Красивое распределение плотности | Это другая визуализация и другая задача |
| **GPU-шейдер** | Попиксельный расчёт на видеокарте | Тысячи потоков, реальное время | Нужен GPU-код, ограничена точность `float` |

**Известное ограничение Мариани–Сильвера.** Теорема о связности верна для *точного* множества, а на растре возможны «тонкие нити» (филаменты), проходящие внутри блока и не пересекающие его границу в пикселях. Тогда блок ошибочно заливается. Практически это единицы пикселей. На тестовых видах отличие от попиксельного рендера составило от 0 до 0,004 % пикселей. Уменьшение `Мин. размер блока` и рост `Макс. итераций` снижают такую вероятность.

### 2.4. Как устроена программа

```
 UI-поток (WinForms)                         Рабочий поток (Task)
 ───────────────────                         ────────────────────
 кнопка «Рекурсивный рендер»  ───────►  MarianiSilverRenderer.Run()
        │                                       │
        │                                       ▼
        │                              Process(...) — рекурсия
        │                                       │ после КАЖДОГО блока:
        │                                       │  • пишет цвета в _pixels[]
        │                                       │  • рисует рамку в _overlay[] (цвет = глубина)
        │                                       │  • запоминает текущий блок
        │                                       │  • каждые N блоков — Sleep(16 мс)
        ▼                                       ▼
 Timer (30 мс) ◄──── общие буферы _pixels / _overlay / RenderStats
   • собирает _display = фрактал + рамки
   • копирует в Bitmap (LockBits + Marshal.Copy)
   • рисует белую рамку вокруг текущего блока
   • обновляет панель статистики
```

Ключевые решения:

- **Ядро отделено от UI.** `MandelbrotCore.cs` не использует `System.Drawing`, поэтому его легко тестировать.
- **Визуализация без блокировки интерфейса.** Расчёт идёт в `Task`, а картинку обновляет таймер.
- **Замедление регулируется ползунком** («блоков за кадр»): от одного шага за кадр, когда видно каждую итерацию рекурсии, до сотен шагов за кадр.
- **Отмена.** Рекурсия на каждом вызове проверяет `CancellationToken`; новый клик по картинке мгновенно прерывает старый расчёт.
- **Буфер `int[]` + `LockBits`** вместо `SetPixel` — это на порядок быстрее.

### 2.5. Визуализация рекурсии

При включённом флажке «Визуализировать рекурсию» вы видите:

- **Цветные рамки блоков.** Цвет рамки соответствует глубине рекурсии (легенда на панели справа: 0 — весь экран, 1 — квадранты и так далее).
- **Белую рамку** — блок, обрабатываемый прямо сейчас.
- **Заливку «целиком»** — внутри больших однородных блоков картинка появляется мгновенно, без вычислений. Это и есть выигрыш алгоритма.
- **Мелкую сетку у границы множества** — там соседние пиксели различаются, блоки дробятся до `Мин. размера блока`.
- **Статистику:** число разбиений, залитых блоков, листьев, максимальную и текущую глубину, долю реально вычисленных пикселей.

### 2.6. Инструкция по использованию

| Элемент | Назначение |
|---|---|
| **Макс. итераций** | Точность. Чем больше, тем детальнее граница, но дольше расчёт. При сильном зуме поднимайте до 1000–3000 |
| **Мин. размер блока** | При каком размере блока рекурсия прекращается и пиксели считаются напрямую (2–32) |
| **Визуализировать рекурсию** | Включает пошаговую анимацию. Выключите для быстрого рендера |
| **Показывать границы блоков** | Показывает или скрывает цветные рамки (можно переключать и после расчёта) |
| **Скорость визуализации** | Сколько блоков обрабатывается за один кадр |
| **▶ Рекурсивный рендер** | Запуск алгоритма Мариани–Сильвера |
| **Классический попиксельный рендер** | Запуск обычного алгоритма. Сравните время и число вычисленных пикселей в статистике |
| **■ Остановить** | Прервать расчёт |
| **⌂ Сбросить вид** | Вернуться к начальному виду |
| **ЛКМ по картинке** | Приблизить ×2 в точке клика |
| **ПКМ по картинке** | Отдалить ×2 |

**Рекомендуемый сценарий демонстрации:**

1. Запустите программу — рекурсия стартует сама. Убавьте скорость и посмотрите, как строится квадродерево.
2. Дождитесь конца, затем нажмите **«Классический попиксельный рендер»** и сравните строки «Время» и «Вычислено пикселей».
3. Кликните ЛКМ по границе множества (например, около точки `−0.745 + 0.113i`) несколько раз — это известная «Долина морских коньков». Поднимите `Макс. итераций` до 800–1500.
4. Выключите «Визуализировать рекурсию» для быстрого зума и включите обратно, когда нужно показать работу алгоритма.

**Пределы.** Используется `double`, поэтому максимальный полезный зум — около ×4·10¹⁰ (размер пикселя ≈ 10⁻¹³). Глубже появляется «пикселизация» из-за потери точности (в программе зум дальше блокируется).

## 3. Приложение 2 — HanoiApp (Ханойские башни)

### 3.1. Правила

Три стержня (A, B, C), `N` дисков разного размера (3–10, по умолчанию 5). Изначально все диски на стержне A в виде пирамиды. Цель — перенести пирамиду на B или C.

- За ход переносится **один** диск (верхний со стержня).
- **Нельзя** класть больший диск на меньший.
- Минимальное число ходов для `N` дисков равно `2ⁿ − 1` (для 8 дисков — 255).

### 3.2. Рекурсивный алгоритм

Пусть `Solve(k, t)` — «переместить диски `1..k` на стержень `t`». Тогда:

```
Solve(k, t):
    если k = 0 → ничего не делать                            ← база рекурсии
    src ← стержень, где сейчас лежит диск k
    если src = t → Solve(k−1, t); вернуться                  ← диск k уже на месте
    other ← третий стержень (не src и не t)
    Solve(k−1, other)        // 1. убрать меньшие диски с дороги
    переложить диск k: src → t // 2. переложить самый большой
    Solve(k−1, t)            // 3. вернуть меньшие диски сверху
```

**Анализ.** Число ходов удовлетворяет рекуррентному соотношению `T(n) = 2·T(n−1) + 1`, `T(0) = 0`. Решение: `T(n) = 2ⁿ − 1`. Это **оптимально**: самый большой диск должен хотя бы раз переехать, и в этот момент все меньшие диски обязаны лежать на третьем стержне — отсюда та же рекуррентность и для нижней оценки.

Глубина рекурсии равна `N + 1`, так что для практических значений `N` переполнения стека не будет. Время работы экспоненциально — `O(2ⁿ)`, но это свойство самой задачи (ходов столько и должно быть), а не недостаток алгоритма.

**Особенность реализации — решение из любого положения.** Классический алгоритм предполагает начальное положение «все диски на A». Здесь функция читает реальное положение диска `k` (`pegOf[k]`), поэтому после ваших собственных ходов кнопки «Решить» **продолжат игру из текущего положения** и построят оптимальную цепочку ходов до цели. Цель выбирается автоматически: стержень, на котором лежит самый большой диск (его тогда не придётся двигать); если он на A — стержень C.

### 3.3. Дополнительное задание — решение через стек

`SolveWithStack` делает ровно то же самое, но **без рекурсивных вызовов**. Стек вызовов эмулируется явной структурой `Stack<Frame>`, где `Frame = (k, target, stage)`:

- `stage 0` — подзадача ещё не начата: разворачиваем её в две новые подзадачи;
- `stage 1` — подзадача `k−1` уже решена, теперь нужно переложить диск `k` и поставить на стек возврат меньших дисков.

```
push(Frame(n, target, 0))
пока стек не пуст:
    f ← pop()
    если f.k = 0 → продолжить
    если f.stage = 0:
        если диск k уже на цели  → push(Frame(k−1, target, 0))
        иначе push(Frame(k, target, 1));          // «потом»
              push(Frame(k−1, other,  0))          // «сейчас»
    иначе:
        ход: диск k → target
        push(Frame(k−1, target, 0))
```

Важный момент: в стек кладём в **обратном** порядке — сначала то, что нужно сделать позже, затем то, что нужно сделать сейчас (LIFO).

| | Рекурсия | Явный стек |
|---|---|---|
| Читаемость | Очень высокая, код повторяет определение | Ниже, нужно вручную хранить «стадии» |
| Память | Системный стек вызовов (ограничен ≈1 МБ на поток) | Куча — ограничена только ОЗУ |
| Риск `StackOverflow` | Есть при очень глубокой рекурсии | Нет |
| Результат | Идентичная последовательность ходов | Идентичная последовательность ходов |

В статусной строке программа показывает макс. глубину рекурсии (или макс. размер стека) для выполненного решения.

### 3.4. Чем рекурсивное решение отличается от других

| Подход | Суть | Особенность |
|---|---|---|
| **Рекурсия** (основной) | Разбиение на подзадачи `N−1` | Самое наглядное, оптимально, работает из любого положения |
| **Явный стек** | То же, но без вызовов функций | Устойчив к большой глубине, чуть сложнее |
| **Итеративный по чётности** | Чередуем: ход самого маленького диска по кругу (A→B→C для чётного `N`, A→C→B для нечётного), затем единственный допустимый ход без него | Не нужен ни стек, ни рекурсия, но работает только из начального положения |
| **Код Грея / двоичный счётчик** | Номер хода в двоичной записи определяет, какой диск двигать | Позволяет вычислить `i`-й ход за `O(1)` |
| **Frame–Stewart** | Вариант для 4 и более стержней | Другая задача |

### 3.5. Как устроена программа

```
 HanoiGame (модель)          HanoiSolver (алгоритмы)        MainForm (UI)
 ──────────────────          ───────────────────────        ─────────────
 Pegs: List<int>[3]          SolveRecursive(pegOf,…)        • рисует стержни/диски (GDI+)
 CanMove / Move / Undo       SolveWithStack(pegOf,…)        • мышь: клик / drag-and-drop
 History: List<Move>         → List<Move> + статистика      • очередь ходов Queue<Move>
 IsSolved                                                   • таймер 16 мс: анимация
```

Поток работы автоматического решения:

1. Кнопка «Решить» → `GetPegOfDisk()` снимает текущее положение.
2. Решатель **целиком** строит список ходов `List<Move>` (это быстро: даже `2¹⁰−1 = 1023` хода — доли миллисекунды).
3. Ходы кладутся в `Queue<Move>`.
4. Таймер по одному извлекает ход, применяет его к модели и запускает анимацию: **подъём → перенос по горизонтали → опускание**. Диск, который сейчас «летит», не рисуется на стержне, чтобы не двоиться.
5. Когда очередь опустела, проверяется победа.

Такое разделение (сначала «вычислить», потом «показать») — стандартный приём визуализации алгоритмов: логика не зависит от скорости анимации и может тестироваться отдельно.

### 3.6. Инструкция по использованию

| Действие | Как |
|---|---|
| Взять и переложить диск | **Клик** по стержню (верхний диск приподнимется) → **клик** по другому стержню |
| То же перетаскиванием | Зажать ЛКМ на стержне → перетащить диск → отпустить над нужным стержнем |
| Отменить выбор | ПКМ |
| **Дисков** | Количество дисков 3–10 (изменение начинает новую игру) |
| **Новая игра** | Сброс |
| **Отменить ход** | Откат последнего хода |
| **Решить (рекурсия)** | Анимированное решение рекурсивным алгоритмом из текущего положения |
| **Решить (стек)** | То же, но алгоритмом с явным стеком |
| **Стоп** | Остановить автоматическое решение |
| **Скорость** | Скорость анимации (от ~1 с до ~25 мс на ход) |

Сверху отображаются счётчик ходов, теоретический минимум `2ⁿ − 1` и таймер. При попытке положить больший диск на меньший стержень на мгновение подсвечивается красным, а в строке состояния появляется сообщение. После победы выводится окно с результатом (число ходов, время, сравнение с минимумом).

## 5. Проверка корректности

Ядро обоих приложений (`MandelbrotCore.cs`, `HanoiGame.cs`, `HanoiSolver.cs`) не зависит от WinForms, поэтому было проверено консольными тестами на .NET 8:

**Ханойские башни**
- Для `N = 1…12` оба алгоритма приводят всю башню на стержень C, число ходов в точности равно `2ⁿ − 1`, все ходы допустимы.
- 2000 случайных допустимых положений (3–8 дисков): оба решателя приходят к цели, не нарушают правил, и **последовательности ходов рекурсии и стека совпадают**.

**Мандельброт** (800×600), сравнение рекурсивного рендера с попиксельным:

| Вид | Итераций | Время рекурс. / классич. | Пикселей вычислено | Отличающихся пикселей |
|---|---|---|---|---|
| Общий вид | 300 | 57 / 67 мс | 43,7 % | 0 |
| «Долина морских коньков» | 800 | 800 / 1223 мс | 76,4 % | 19 (0,004 %) |
| «Игла» (−1,25 + 0,02i) | 500 | 271 / 1660 мс | 16,9 % | 7 (0,001 %) |
| Дендрит у верхней границы | 600 | 222 / 406 мс | 68,6 % | 0 |

Замеры сделаны на серверном процессоре в один поток; на вашем компьютере цифры будут другими, но соотношение сохранится. Чем больше на изображении однородных областей, тем выше выигрыш (на «игле» — примерно в 6 раз).
